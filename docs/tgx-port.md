## 1. 为什么需要 AC6

TGX 用了 C++17 特性：`if constexpr`（140+ 处）、`template<auto>`（Rasterizer.h）。

- 原工程是 **AC5**（只到 C++03）→ 无法编译
- 已整体切换为 **ARM Compiler 6.7**（`uAC6=1`）

### 切换中踩到的三个坑

| # | 现象 | 原因 | 处理 |
|---|---|---|---|
| 1 | `cmsis_armclang_ltm.h` file not found（43 处） | 板包里的 CMSIS 版本较新，把 AC6.6/6.7 路由到一个**未随包提供**的 ltm 头 | 改 `Drivers/CMSIS/Include/cmsis_compiler.h`：`< 6100100` 分支改为包含 `cmsis_armclang.h`（已备份原文件） |
| 2 | `'auto' not allowed in template parameter until C++1z` | uVision 5.24 的 C++ 标准下拉最高只到 C++14 | 给**每个 .cpp** 加文件级 `-std=c++1z -fno-exceptions -fno-rtti` |
| 3 | 加了文件级选项后，**汇编器**报 `invalid argument '-std=c++1z' not allowed with 'C/ObjC'`；随后所有 .cpp 不再参与编译 | `<FileOption>` 块字段不全（uVision 按"覆盖全局"理解），且 `<IncludeInBuild>0</IncludeInBuild>` = **从构建中排除** | 按 uVision 自身写出的完整 `<Cads>` schema 补齐；`IncludeInBuild` 设为 **1** |

> 这三条都固化在 `DSH/middleware/patch_cpp_file_options.py` 里，可重复执行。

### 最终编译选项

| 项 | 值 |
|---|---|
| 编译器 | ARM Compiler 6.7（`-O2`，`<Optim>2</Optim>`） |
| 告警级别 | `<wLevel>1</wLevel>`（HAL 在 wLevel=2 下会产生 467 条 `-Wpadded/-Wconversion` 噪音） |
| C++ 标准 | 文件级 `-std=c++1z -fno-exceptions -fno-rtti` |
| 代码/常量 | Code **100,084 B**、RO 15,328 B（含 TGX ≈ +46 KB） |
| ZI | 2,139,812 B（其中 750 KB 帧缓冲 + 64 KB 纹理 + 32 KB RGB565 纹理） |

## 4. 首次实测数据（2026-11-15 10:00）

| 项目 | 吞吐 | 折算 cycles/px |
|---|---|---|
| 纯填充（800×480×10） | **77.04 Mpx/s** | ≈ 6.2 |
| 纹理四边形（双线性+alpha，RGB32 源） | 1.59 Mpx/s | ≈ 302 |
| 类 Spine 小三角形（渐变+alpha） | 1.40 Mpx/s | ≈ 343 |

### 初步解读（待矩阵数据确认）

- **填充率正常**：6.2 cycles/px 说明 SDRAM 写通路与 Cache 行为健康（LTDC 扫描同时进行）。
- **纹理路径异常慢**：约 300 cycles/px，是填充的 50 倍。这个数量级不像"双线性 + 4 次纹理采样"的正常开销（预期 40–80 cycles/px）。
- 待排查方向（矩阵测试正是为此设计）：
  1. RGB32（ARGB8888）源纹理 → 每像素 4 次 32-bit 采样 + 浮点插值 + alpha 混合；
  2. 纹理常驻 **AXI SRAM**，但 `mpu.c` 对其配置可能是非 cacheable（需确认）；
  3. 目标为 SDRAM framebuffer 且同时被 LTDC 读取，缓存行争用；
  4. TGX 2D 纹理路径是否有逐像素除法（透视校正）。

### 对 Spine 的含义

若纹理路径维持 ~1.5 Mpx/s：

| 角色覆盖像素 | 单帧渲染 | 等效帧率 |
|---|---|---|
| 60 k（半身 300×400） | ≈ 40 ms | ≈ 25 fps |
| 180 k（全身 500×600） | ≈ 120 ms | ≈ 8 fps |

即**当前配置不足以支撑 30 fps 的角色动画**，必须先解决纹理路径性能（这是 Phase 0 的核心价值：在写业务代码前暴露问题）。

## 6. 对照矩阵实测（2026-11-15 10:20，第二次成功跑板）

| 配置 | 吞吐 | ≈cycles/px | 相对填充 |
|---|---|---|---|
| 纯填充（RGB565） | **77.53 Mpx/s** | 6.2 | 1× |
| 纹理 565 源 + 覆盖写 | 2.73 Mpx/s | 176 | 28× |
| 纹理 32 源 + 覆盖写 | 2.03 Mpx/s | 236 | 38× |
| 纹理 32 源 + alpha 混合 | 1.57 Mpx/s | 306 | 49× |
| 渐变三角形（类 Spine） | 1.44 Mpx/s | 333 | 54× |

### 结论：瓶颈在「双线性纹理采样 + 着色器 ALU」，不在带宽/格式

拆解增量：

- RGB565 → RGB32 源纹理：−26%（32-bit 采样 + 每像素格式转换）
- 打开 alpha 混合：−23%（每像素浮点混合 + 往返转换）
- 再加顶点色渐变：−9%

也就是说，**最裸的双线性纹理四边形就已经是 176 cycles/px**，是填充的 28 倍。
按 384k 像素/帧算，理论上限约 2.7 Mpx/s —— 与实测一致，说明测量与实现都是"如实"的。

### 对 Spine 的含义（按 tris=1.44 Mpx/s）

| 角色覆盖 | 单帧 | 帧率 |
|---|---|---|
| 60 k px（半身 300×400） | 41.7 ms | **24 fps** |
| 180 k px（全身 500×600） | 125 ms | **8 fps** |
| 384 k px（满屏） | 267 ms | 3.7 fps |

需要优化才能在 800×480 上跑 30 fps 角色动画。

### 可选的优化方向（待评估）

| # | 方案 | 预期 |
|---|---|---|
| 1 | 降低渲染分辨率（如 400×240 后由 LTDC 放大） | 像素数 ×0.25 → 约 4 倍提升 |
| 2 | 只重绘角色包围盒（脏矩形），背景不重绘 | 视场景省 30–70% |
| 3 | 自定义**点采样 + 预乘 alpha** 的专用光栅器替换 TGX 双线性路径 | 目标 30–50 cyc/px（3–5 倍） |
| 4 | 纹理用 RGB565/ARGB1555 取代 ARGB8888 | −26%（单独看） |
| 5 | 把纹理放 DTCM（128 KB 可用，当前只用了默认 AXI） | 待测（缓存实验已写好但未烧入） |

> 说明：TGX 2D 的纹理三角/四边形**只有双线性一种采样方式**（点采样只在 3D 渲染器里），
> 若要走第 3 条路，需要自己写 shader 分支或另起一个精简光栅器。

## 7. 烧写稳定性问题（环境侧，需注意）

本次调试中出现多次 ST-Link 写入失败，之后调试口完全无响应：

```
Error: Failed to write memory and, additionally, failed to find out where
Error: Fail reading CTRL/STAT register. Force reconnect
Error: read version failed            ← 之后每次连接都报这个
```

观察到的规律与处理：

| 现象 | 说明 |
|---|---|
| `read version failed` 持续 | ST-Link 固件级卡死，**只能拔插 USB**（有时等 45–90 s 自愈） |
| 失败发生在写 flash 阶段 | 目标端调试口失联（CTRL/STAT 读失败），非 SWD 速率问题（1 MHz 仍失败） |
| 成功过的配置 | 烧写时**串口 COM11 保持打开**（CH340 的 DTR/RTS 驱动 BOOT0/NRST，关闭时 RTS 悬空可能拉低 NRST） |
| 建议 | 烧写前先打开串口（或用 10 kΩ 上拉 RTS）；SWD 速率降到 1–2 MHz；必要时换 USB 口/短线 |

已把 `flash.sh` 的 SWD 速率改为可配置（默认 1000 kHz）。

## 8. 点采样改造 + 最终数据（2026-11-15 11:00）

### 改造内容

给 TGX 2D 纹理着色器加了一个宏开关 `TGX_TEXTURE_POINT`（`DSH/middleware/patch_tgx_point_sampling.py`）：

```cpp
#if defined(TGX_TEXTURE_POINT)
    color_t_tex col = tex[((ax < 0.5f) ? minx : maxx) + ((ay < 0.5f) ? miny : maxy)];   /* 最近邻 */
#else
    color_t_tex col = interpolateColorsBilinear(...);                                   /* 原 4 抽头 */
#endif
```

默认宏在 `Middlewares/TGX/tgx.h` 中打开；不定义则与原库行为一致。

### 效果对比

| 配置 | 双线性 | 点采样 | 提升 |
|---|---|---|---|
| 纹理 565 + 覆盖写 | 2.73 Mpx/s (176 cyc/px) | **4.69 Mpx/s (102 cyc/px)** | +72% |
| 纹理 32 + 覆盖写 | 2.03 | 3.65 | +80% |
| 纹理 32 + alpha 混合 | 1.57 | 2.49 | +59% |
| 渐变三角形（类 Spine） | 1.44 | **2.07 Mpx/s** | +44% |

> 顺带确认：8 KB 纹理（完整放进 16 KB D-Cache）与 32 KB 纹理吞吐**完全相同**（4.68 vs 4.69）
> → 瓶颈与 Cache 无关，是纯 ALU/指令开销。

### 折算帧率（点采样，tris=2.07 Mpx/s）

| 角色覆盖 | 单帧 | 帧率 |
|---|---|---|
| 60 k px（半身 300×400，约 50% 覆盖） | 29 ms | **≈34 fps** |
| 120 k px | 58 ms | ≈17 fps |
| 180 k px（全身 500×600） | 87 ms | ≈11 fps |
| 384 k px（满屏） | 185 ms | ≈5 fps |

**结论**：点采样后，**半身级角色（≤60k 覆盖像素）可以做到 30 fps 以上**；全身/满屏级仍需优化。

## 9. 踩到的一个隐蔽 bug：栈只有 2 KB（已修）

### 现象

TGX 图形绘制正常，但屏幕上的**文字和 DMA2D 填充全部静默失效**（串口数据正常）。

### 定位过程

1. 分析 framebuffer dump：文字区域没有像素 → 不是颜色/坐标问题。
2. 怀疑 DMA2D/Cache 顺序，按 clean→DMA→invalidate 改了一版，**仍然无效**。
3. 用 SWD 直接读 `lcddev` / `lcdltdc` 结构体（map 查出地址 0x2401fe92 / 0x2401fe9c）：
   `pwidth = 0`、`pheight = 0x1CD`…**结构体被垃圾数据覆盖**。
4. 查 map 布局发现：
   ```
   lcdltdc    0x2401fe9c  (36 B)
   uwTick     0x2401fec0
   Stack_Mem  0x2401fec8  (2048 B)   <-- 栈只有 2 KB
   ```
   栈就在这些全局变量上方，**TGX 模板的深调用链把 2 KB 栈溢出**，直接冲掉了下方的 LCD 状态。

### 修复

`startup_stm32h743xx.s`：`Stack_Size 0x800 (2 KB) → 0x4000 (16 KB)`（已备份原文件）。

修复后文字、DMA2D 色带全部正常——**这个问题在接入 Spine 时同样会咬人**（spine-cpp 的解析/更新调用更深），
所以这次提前发现很有价值。

## 12. 自写光栅器最小原型验证（2026-11-15 12:00）

## 13. 生产版光栅器 raster2d —— 完整功能 + 优化后性能

### 13.1 功能（`Middlewares/RASTER/raster2d.{h,cpp}`，约 550 行）

回归测试 `User/raster_test.cpp`：**5/5 全过**。

### 13.2 三轮优化的效果（每轮都实测）

| 负载 | 初版 | ①扫描线区间 | ②强制内联 | ③再加 -O3 | TGX 点采样 |
|---|---|---|---|---|---|
| 四边形 覆盖写 | 8.2 | 24.8 | 25.0 | **27.7 Mpx/s** | 4.69（-O3 后 3.64*） |
| 网格 565 逐顶点色 | 2.8 | 2.0 | 5.05 | **5.50** | — |
| 网格 4444 逐顶点色 | 1.4 | 1.54 | 3.41 | **3.56** | 2.07（-O3 后 **3.09**） |

> \* 注意：`-O3` 同时应用到了 TGX，TGX 自身也提速约 50%（tris 2.07 → 3.09，texquad 2.49 → 3.64）。
> 因此**与 TGX 的公平对比应使用 -O3 后的数字**：典型色调负载 3.56 vs 3.09，只快约 15%；
> 覆盖写 27.7 vs 4.69，快 5.9 倍。

**三个关键发现（都是实测出来的）**：

1. **内层逐像素边界判定是主要开销**：改成"每行解出 x 区间 + 端点用定点边函数校验"后，
   覆盖写从 8.2 → 24.8 Mpx/s（3 倍），且 top-left 语义完全保持（T1/T2 仍通过）。
   注意：浮点区间可能偏窄 1–2 px，必须**向外扩展**（否则出现 13 个像素的接缝）。
2. **`mul255`/`pack565` 没有被内联**（反汇编看到 `_ZL6mul255ii PROC` + 每像素 4–6 次 BL），
   加 `__attribute__((always_inline))` 后色调路径 2.2 → 5.8 Mpx/s（2.6 倍）。
3. `-O3` 再给 5–10%。

### 13.3 现状与目标差距

| 角色覆盖 | 生产版（4444+色调 3.56） | 目标 30 fps |
|---|---|---|
| 60 k px | 17 ms → **59 fps** ✅ | 满足 |
| 120 k px | 34 ms → 30 fps | 刚好 |
| 180 k px | 51 ms → 20 fps | 不足 |

覆盖写路径已经超过原型（27.7 vs 20.3），**瓶颈集中在"逐顶点色调 + ARGB4444 解包 + 8bit 往返"**。

### 13.4 565 原生混合 + 三档色调（本轮实现）

实现内容：

* **`lerp565()`**：NORMAL 混合直接在 RGB565 空间逐通道 lerp，不再 unpack dst / pack 回写；
* **`add565()`**：加法混合的 565 原生饱和加；
* **COLMODE 三档**：
  * `0` 常量色（整三角形同色）——最常见
  * `1` RGB 恒定、仅 alpha 逐顶点变化（**Spine slot alpha，最常见的逐顶点情况**）
  * `2` 完整逐顶点 ARGB

实测（-O3）：

| 负载 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| 四边形 · 常量色调（不透明） | — | **9.13 Mpx/s** | COLMODE 0 |
| 四边形 · 仅 alpha 变化（4444） | — | **4.44** | COLMODE 1 |
| 网格 · 仅 alpha 变化（4444） | — | **4.15** | COLMODE 1 |
| 网格 · 完整逐顶点（4444） | 3.56 | 3.45 | COLMODE 2 |
| 四边形 · 覆盖写 | 27.7 | **27.8** | RAW_COPY |

**结论：565 原生混合的收益集中在"常量色调"路径（9.13 Mpx/s）；完整逐顶点路径几乎没变。**

原因是：完整逐顶点时，每像素仍要做 ARGB4444 解包（3 次 ×17）+ 3 通道插值 + 4 次钳位，
这部分占总开销的 2/3，565 原生混合只省下了 unpack/pack 那十几条指令。

### 13.5 ARGB1555 实测：比 4444 快约 2 倍（推荐纹理格式）

素材可控 → 图集直接导成 **ARGB1555**（1 bit alpha，省掉 4444 的 3 次 ×17 展开）：

| 负载 | ARGB4444 | **ARGB1555** | 提升 |
|---|---|---|---|
| 网格 · 完整逐顶点 | 3.46 Mpx/s | **6.82 Mpx/s** | **1.97×** |
| 四边形 · 常量色调 | 4.44（alpha-only） | **11.20** | 2.5× |
| 四边形 · 565 常量色调（参考） | — | 9.13 | — |
| 覆盖写 | 27.8 | 27.8 | — |

折算帧率（6.82 Mpx/s）：

| 角色覆盖 | 单帧 | 帧率 |
|---|---|---|
| 60 k px（半身） | 8.8 ms | **114 fps** |
| 120 k px | 17.6 ms | 57 fps |
| 180 k px（全身） | 26.4 ms | **38 fps** |
| 240 k px | 35 ms | 28 fps |

**结论：换成 ARGB1555 后，180k 像素的全身角色从 20 fps 提升到 38 fps，达标。**

### 13.6 纹理格式建议（素材侧）

raster2d 的 `fmt` 是**逐纹理**参数，所以可以混用：

| 素材类型 | 推荐格式 | 理由 |
|---|---|---|
| 硬边角色部件（主体、武器、UI 图标） | **ARGB1555** | 2× 吞吐，硬边无损失 |
| 需要柔和边缘（发光、软阴影、半透明特效） | ARGB4444 | 1 bit alpha 会有锯齿 |
| 完全不透明（背景块） | RGB565 + 色键 | 最快（可走 RAW_COPY 27.8） |
